# 实验设计：黑盒反馈下 LLM 的算法代码调试能力

## 1. 研究假设

- H1（头版）：TLE 类（算法复杂度不足）修复率显著低于 WA 类（实现错误）——
  TLE 需要算法级重构，黑盒反馈无法提供热点定位信息。
- H2：伪修复（过可见样例、挂隐藏测试）真实存在，且在需要特判的边界类题目上更高。
- H3：黑盒反馈相对白盒反馈（提供失败样例输入输出）造成显著性能损失。
- H4：自我修复（阶段 A）与受控注错（阶段 B）中，模型表现模式一致（补丁倾向 vs 重写倾向）。

## 2. 题库设计（problems/）

每题一个目录：`problem.json`（含洛谷 source）+ `solution.cpp`（参考解，阶段 B 用）
+ `mutants/`（注错变体）。题面/样例/时限从洛谷拉取缓存（platform_cache.json）。

三类题各 ~8 道：

1. **classic**：洛谷已有经典题（如 P1908 逆序对），训练数据必然见过；
2. **reskin**：同构换皮——上传为洛谷**个人私有题目**，换叙事背景改变量名；
3. **novel**：自编新构——微调约束使经典模板恰好失效，同样上传个人私有题目。

> 防污染：reskin/novel 全部自编并上传私有题库，不进公开题库；classic 作对照基线。
> 隐藏测试 = 洛谷该题全部测试点（对选手不可见）；可见样例 = 题面样例。

## 3. 交互协议（真实 OJ 平台判题，洛谷为主）

模型每轮可调用的工具（function calling）：

| 工具 | 实现 | 反馈 |
|------|------|------|
| `compile(code)` | 本地 g++ | 编译结果（报错全文） |
| `run_sample(code)` | 本地跑题面样例 | 输入/实际输出/期望输出/退出码 |
| `submit(code)` | **提交真实 OJ（洛谷主力 / CF 备选）** | 每个测试点 通过/未通过；未通过标注 WA/TLE/MLE；内容不可见 |

- 最多 K=10 轮提交；编译失败不计轮；
- 每题每模型重复 3 次（固定 temperature 0.7），报告均值±标准差；
- 全程记录每轮代码、工具调用序列、反馈，供后续策略分析。

### 平台选择与依据

| 平台 | 提交 | 结果读取 | 自编题托管 | 定位 |
|------|------|----------|-----------|------|
| 洛谷 | 非官方接口（Cookie） | 逐测试点状态 | ✓ 个人私有题目 | **唯一判题平台** |

**实验节奏约束**：洛谷接口需限速（两次提交强制间隔 ≥60s 保护账号），
单题单模型一轮（≤10 次提交）约 10~15 分钟；全量实验按
题目数 × 模型数 × 3 次重复估算总时长，分批错峰执行。

**本地沙箱仅用于两件事**：gcc 编译（`compile` 工具）与题面样例自测
（`run_sample` 工具）——即真实选手的本地调试能力；正式判题一律走洛谷。

## 4. 阶段设计

### 阶段 A：自我修复
模型仅凭题面写首份代码 → 判题 → 进入调试循环。
（若首份即全过，该题记"首过"，不进循环。）

### 阶段 B：受控注错
对参考解注入四类 bug，各题 × 各类 ≥ 2 个变体：

| bug 类型 | 典型注入 | 预期反馈 |
|----------|----------|----------|
| 边界 | off-by-one、空输入、循环初值 | WA（部分点） |
| 溢出 | int → 需 long long 的规模 | WA（大数点） |
| 复杂度 | 参考解降级为 O(n²) | TLE（大点） |
| 算法思想 | 贪心换为错误贪心 | WA（对抗点） |

注入方式：手写变体 + 人工确认（不依赖自动变异工具，保证 bug 真实自然）。

### 阶段 C：白盒对照
`submit` 反馈改为附失败样例的具体输入/期望输出/实际输出（前 3 个失败点）。
同题同模型对比 → 定位信息的价值。

## 6. 时间线（4~5 周）

| 周 | 内容 |
|----|------|
| 1 | 题库：classic 直接拉洛谷题；reskin/novel 自编并上传洛谷个人私有题目；注错变体 |
| 2 | 洛谷接口联调：Cookie 登录、提交语言代号、记录 status 码映射实测校准 |
| 3 | LLM API function-calling 封装；2 题小规模试跑调通闭环 |
| 4 | 全量实验（A→B→C）；统计出图 |
| 5 | 论文撰写（文献综述已有底稿，重点接"验证鸿沟"叙事） |

## 7. 风险与对策

| 风险 | 对策 |
|------|------|
| 洛谷非官方接口风控/封号 | 专用小号；两次提交强制间隔 ≥60s；错峰分批；如实写入论文局限 |
| 模型不擅长 function calling 时协议执行不稳 | 降级方案：文本协议（输出 JSON 指令），runner 解析执行 |
| AI 本地执行代码的安全 | 本地仅编译与跑题面样例（临时目录 + 超时强杀），无自造测试 |
| 模型直接"记住"经典题（首过率虚高） | 三类题对照，重点看 reskin/novel；首过率本身也是分类指标 |
| API 费用/轮次过多 | 每轮截断历史（保留最近 4 轮 + 首轮）；先试跑再全量 |
