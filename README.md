# LLM 黑盒反馈调试实验（OI 场景）

> 黑盒测试反馈下大模型修改算法代码的能力实验研究
> 本科课程设计项目

## 研究问题

在 OI 式黑盒评测中，提交代码后仅知道：每个样例通过与否，未通过者标注 WA / TLE / MLE，
无法定位具体错在哪。大模型在这种**贫信息反馈**下，能把错误的算法代码修对吗？

## 实验场景

被试（各家 LLM API）获得的信息与工具，与真实 OI 选手对齐：

- 题面（含示例输入/输出）
- 工具 1：`gcc` 本地编译（编译报错完整可见）
- 工具 2：在示例数据上本地运行自测
- 工具 3：提交判题 → 反馈：每个样例 通过/未通过；未通过标注 WA/TLE/MLE
- 测试点**内容**不可见（黑盒），最多 K=10 轮提交

## 实验结构

```
┌─────────────── 阶段 A：自我修复 ───────────────┐
│ 模型自己生成首份代码（往往是错的），然后自己修    │
└──────────────────────────────────────────────┘
┌─────────────── 阶段 B：受控注错 ───────────────┐
│ 往参考解注入已知类型 bug（边界/溢出/复杂度/思想） │
│ → 每类 bug 的修复率有干净地基真值                 │
└──────────────────────────────────────────────┘
┌─────────────── 阶段 C：白盒对照 ───────────────┐
│ 同任务，但反馈附失败样例的具体输入输出（上界）     │
│ 黑盒 vs 白盒差距 = 定位信息缺失的损失             │
└──────────────────────────────────────────────┘
```

## 核心指标

| 指标 | 定义 |
|------|------|
| 首过率 | 第 1 次提交即全过的占比 |
| K 轮修复率 | ≤10 轮内隐藏测试全过的占比 |
| 伪修复率 | 骗过可见样例但挂隐藏测试的占比 |
| 回归率 | 修复过程中改坏此前已通过样例的频率 |
| 分层修复率 | 按 WA / TLE / MLE 与 bug 类型分层 |

**头版假设（H1）**：TLE 类修复率显著低于 WA 类——TLE 意味着算法本身太慢，
黑盒反馈无法指出热点，打补丁无效，必须算法级重构。
